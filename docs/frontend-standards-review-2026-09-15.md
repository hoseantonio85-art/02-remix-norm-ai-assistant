### Детали функциональных дефектов

**Удаление источника.** Если панель открыта со списком `[A, B]`, после удаления B актуальное знание получает `[A]`. Условие `groupedSources.length > currentSources.length` истинно: возвращается старый объект с `[A, B]`. Уведомление при этом сообщает об удалении. Для группы проблема шире: `sourceKnowledgeForGroup` объединяет источники нескольких знаний, но сохраняет id первого знания, а обработчик удаления изменяет только этот id. Дефект установлен по цепочке данных; реальное удаление в пользовательской сессии при ревью не выполнялось.

**Массив с собственным значением.** Для узла `{id:'a', key:'a', valueType:'array', value:'Итого 3', children:[]}` проверка shouldHideNode разрешает показ. Но ArrayRenderer возвращает StateNotice до CompositeOwnValue; собственное значение не отображается. То же возможно, если все дочерние узлы скрыты. Существующий тест собственного значения проверяет только shouldHideNode для объекта — не фактический рендер такого массива. Это отдельный пограничный случай, а не утверждение о потере конкретного значения из текущего файла аналитиков.

## Что уже соответствует

- Подключены корпоративные TypeScript и Biome configs, strict/noUnused сохраняются через наследуемый tsconfig.
- Действующий entrypoint локального preview отделён от Single-SPA lifecycle entrypoint; LocalProductShell не включён в MFE root.
- UI Kit импортируется напрямую. Для KnowledgeGroupAccordion и CircularProgress есть реестр причин отдельной реализации (`docs/ui-kit-candidates.md`), поэтому их наличие не объявлено нарушением само по себе.
- Store использует React context, а не observable MobX: отсутствие observer здесь не является ошибкой.
- Страница KnowledgeBasePage остаётся небольшой композицией с loading/error/retry.
- Адаптеры и renderer имеют регрессионные тесты. Это полезная основа, но не полное покрытие новой UI-логики.
- Открытие панели «Как Норм понимает компанию», доступное имя закрытия, Escape и возврат фокуса проверены в актуальной локальной сборке.

## Допущения и следующий порядок

Текущая цель — рабочий локальный прототип с будущей передачей в продукт, не немедленный production deploy. Порог FAIL означает несоответствие стандартам, а не потерю всех сделанных улучшений.

Порядок исправлений: (1) источники и собственное значение массива + регрессии; (2) тесты store/фильтрации и lint; (3) токены и JSON i18n; (4) структура, публичные API и неиспользуемые файлы; (5) отдельный продуктовый handoff. Внешний вид и факты не нужно переписывать ради этого ревью.
