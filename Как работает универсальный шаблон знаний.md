# Как работает универсальный шаблон знаний

Рабочая версия находится в ветке:

`feature/compact-atomic-presentation`

GitHub:  
https://github.com/hoseantonio85-art/02-remix-norm-ai-assistant/tree/feature/compact-atomic-presentation

## Общая схема

```text
Исходный JSON аналитика
        ↓
Адаптер конкретного формата
        ↓
Универсальная модель знаний
        ↓
Presentation-композиция
        ↓
Аккордеоны и компактные строки интерфейса
```

Сейчас поддерживаются два входных формата:

- `rest_business_object.json`;
- `profile_result_qwen.json`.

Файлы не объединяются между собой: каждый источник отображается как отдельный профиль компании.

## 1. Универсальная модель

Независимо от исходного формата адаптер преобразует данные в девять фиксированных областей:

1. Общая информация.
2. Структура и управление.
3. Собственники и связи.
4. Продукты и бизнес-модель.
5. Операционная деятельность.
6. ИТ, данные и технологии.
7. Финансы.
8. Регуляторика и риск-сигналы.
9. Контрагенты.

Каждое знание получает единый контракт:

- стабильный идентификатор и ключ;
- область `areaId`;
- название;
- состояние данных;
- содержимое `content`;
- метаданные;
- источники;
- при необходимости теги, предупреждения и связи.

## 2. Вложенные данные

Вложенность хранится рекурсивно внутри `content`.

Поддерживаются:

- простое значение;
- длинный текст;
- объект с дочерними полями;
- массив значений;
- массив объектов;
- вложенные массивы и объекты.

Например, «Генеральный директор» может быть одним знанием, внутри которого находятся ФИО, должность, дата назначения, статус и другие атрибуты.

Технические оболочки исходного формата — `fields`, `value`, `metadata`, `nested`, `dependents` — в интерфейсе не показываются. Адаптер раскрывает их и сохраняет полезные значения и метаданные.

## 3. Presentation-композиция

Универсальная модель не содержит указаний, как рисовать данные.

Отдельный presentation-слой группирует атомарные знания в смысловые блоки. Например:

```text
Общая информация
  ├─ Регистрационные сведения
  │    ├─ Краткое наименование
  │    ├─ Полное наименование
  │    ├─ ИНН
  │    ├─ ОГРН
  │    ├─ КПП
  │    └─ Дата регистрации
  ├─ Деятельность компании
  ├─ Описание компании
  └─ Дополнительные сведения
```

Все верхнеуровневые смысловые группы отображаются аккордеонами. Отдельные простые факты внутри группы показываются компактными строками и не превращаются в самостоятельные аккордеоны.

Presentation-группировка не изменяет и не объединяет сами объекты знаний. Она определяет только их расположение на экране.

## 4. Правила отображения

Интерфейс выбирает представление по форме `content`:

- примитив — строка «название — значение»;
- длинный текст — текстовый блок с раскрытием;
- объект — группа вложенных полей;
- массив простых значений — компактный список;
- массив объектов — повторяющиеся вложенные карточки;
- длинный массив — первые три элемента и кнопка «Показать ещё».

Пустой массив не считается автоматически подтверждённым отсутствием данных. Для него должно быть явно определено состояние: `known_empty`, `unknown` или `not_applicable`.

## 5. Метаданные и источники

Каждое знание сохраняет связь с исходным файлом.

В источнике указываются:

- имя JSON-файла;
- тип или dataset;
- дата актуальности;
- при наличии — подтверждение, цитата или место в источнике.

Повторяющиеся технические метаданные не перегружают интерфейс.

Компактная иконка `i` появляется только тогда, когда у конкретного факта есть важные индивидуальные метаданные:

- уверенность;
- значимость для риска;
- срок действия;
- ограничение доступа;
- отдельная цитата или точное место в источнике.

## 6. Что важно фронтенду

Основные части реализации:

- `schemas/universal-knowledge.schema.json` — формальная схема;
- `src/types/universalKnowledge.ts` — TypeScript-типы;
- `src/adapters` — преобразование входных форматов;
- `src/components/UniversalValueRenderer.tsx` — рекурсивный renderer;
- `src/presentation/knowledgePresentation.ts` — группировка знаний для интерфейса;
- `src/data/analystKnowledgeSources.ts` — подключение исходных файлов.

Новые входные форматы следует добавлять через новый адаптер. Логику конкретного формата не нужно переносить в UI-компоненты.

## 7. Что важно согласовать с аналитиками

Для стабильной промышленной интеграции желательно определить:

- целевой входной формат или перечень поддерживаемых форматов;
- стабильные ключи полей;
- правила распределения полей по девяти областям;
- значение `null`, отсутствующего ключа и пустого массива;
- стабильные идентификаторы элементов коллекций;
- правила обновления и удаления фактов;
- обязательность источника и даты актуальности;
- формат индивидуальных метаданных;
- поведение при появлении неизвестного нового ключа.

Текущая реализация не теряет неизвестные поля: они попадают в группу «Дополнительные сведения».

## 8. Текущий результат проверки

- `rest_business_object.json`: 46 знаний, 22 смысловых аккордеона;
- `profile_result_qwen.json`: 39 знаний, 20 смысловых аккордеонов;
- вложенные объекты и коллекции сохраняются;
- локальные JSON побайтно совпадают с актуальными исходниками;
- каждое отображаемое значение прослеживается до исходного файла;
- presentation-группировка не теряет знания;
- все 20 автоматических тестов проходят.
